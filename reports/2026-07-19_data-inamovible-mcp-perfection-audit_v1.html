Decisión: ¿MCP, o CLI directo?

Recomendación: Opción C — Híbrido, CLI-primario. Enviar un CLI delgado witt-di query|resolve|fetch como front door robusto y siempre-disponible, y degradar el MCP a enhancement opcional (descubrimiento agent-native). No dejar el MCP como único front door (A); no borrarlo (B).

Por qué funciona sin perder calidad: el transporte es ortogonal a qué RAG se consulta — rag_backend.query() es la única llamada compartida y el env elige backend (re-verificado en vivo). Un CLI llama al MISMO backend denso contra el MISMO Neo4j hosted → misma calidad 0.80. Lo que el CLI elimina son los dos hazards operativos que están mordiendo ahora mismo: el registro por-sesión que falla en silencio (esta sesión: cero tools DI) y la staleness del pipe stdio. Costo de migración bajo: envuelve rag_backend.py + resolve_id.py que ya existen.

Matiz importante: el MCP no es un hazard de integridad de datos (front door read-only, gate humano no evadible, secretos a salvo). Es un hazard de confiabilidad: fallos silenciosos. Por eso, sea cual sea el transporte, lo no-negociable es (1) el marcador de degradación in-band y (2) gatear el primer arranque en smoke_rag.py → 6/6. resolve_id.py debe seguir siendo el resolver determinista autoritativo dentro de scripts — nunca rutear un lookup determinable por una red.
