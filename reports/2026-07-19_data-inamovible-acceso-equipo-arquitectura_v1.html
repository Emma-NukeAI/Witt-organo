DATA INAMOVIBLE — acceso para el equipo de Latido

Una sola verdad · varias puertas · la mutación SIEMPRE pasa por gate humano · 2026-07-19

La idea en una línea: no se crea una web app "aparte". Se agrega una puerta read-only más a la misma DATA INAMOVIBLE (mismo backend, mismo Neo4j/MinIO, mismo repo). Los médicos consultan y revisan todo; nadie muta sin gate humano. Los secretos viven en el servidor — jamás se reparten.

Superficie READ-ONLY (para todos, "en su totalidad")

  • query — búsqueda semántica GraphRAG
  • resolve — identificadores verificados
  • fetch_raw — bajar al dato crudo (URLs + sha256)
  • browse — recorrer corpus / niches / DBs / entidades / frescura

Superficie de MUTACIÓN (SIEMPRE human-gated)

  • add_dataset → propuesta pending_review
  • gate estructural is_approved() — lo no-aprobado NO entra
  • approve_dataset / ingest_service admin → ingest (embed + MERGE)
  • No expuesta a los médicos. Nunca automática.

Neo4j GraphRAG (vector 1536 + grafo) · MinIO (crudo) · secretos en el env del servidor (NEO4J / OPENAI / MINIO) — nunca en la máquina de un médico. Es el mismo rag_backend.py del repo que ya usan MCP y CLI.

Rollout — prueba pequeño antes de armar bien

  • Fase 1 (MVP): rag_index/query_service/ (FastAPI read-only, hermano del ingest_service) que envuelve rag_backend → /query /resolve /fetch /browse. Auth simple (magic-link o password compartido para empezar). Página web mínima. Deploy al mismo Dokploy. Validar con 1–2 médicos.
  • Fase 2: respuesta redactada por Claude desde las fuentes + citas (lenguaje natural, lo que un médico espera) · UI de revisión del corpus completo · WhatsApp.
  • Invariante: read-only siempre; ingesta/embedding intactos y human-gated; un solo backend.
