# ADR-0048 — `query_service`: el front door HTTP de solo lectura para la webapp (espejo del sobre, status NO-SPEND, identidad de 5 cuentas, índice de históricos)

- **Status:** Accepted — bloque 2 del plan webapp, ejecutado 2026-08-09 bajo las decisiones del fundador registradas en ADR-0047 (Postgres en Dokploy · backend persiste/webapp lee · red interna Dokploy, webapp única superficie expuesta).
- **Relates:** ADR-0043 (el sobre `{degraded, n_hits, hits, last_error, index_version, store_version}`), ADR-0046 (históricos consultables desde la webapp), ADR-0047 (las cinco decisiones + bloque 1.4), ADR-0040 (front door híbrido — este servicio es la tercera puerta, HTTP), ADR-0039 (trampas del MCP heredadas), ADR-0033 (dirección: nada nuevo expuesto al público).
- **Affects:** **NUEVO** `rag_index/query_service/` (`app.py`, `db.py`, `seed_users.py`, `smoke_query_service.py`, `requirements.txt`, `Dockerfile`, `README.md`) · `rag_index/mcp_server/server.py` (pool configurable vía `DI_QUERY_POOL_SIZE`) · `.gitignore` (+`backend.db`). **Cero mutación de la DATA INAMOVIBLE; cero endpoints de escritura sobre ella.**

## Context

La UI no tenía ninguna puerta HTTP de lectura: las únicas 5 rutas del repo eran del ingest_service, y las tres puertas de lectura existentes (MCP stdio, CLI como proceso, import directo) o cambiaban la semántica del dato según la puerta o eran inviables desde un navegador (tapón 4 del handoff webapp). Además `cli health` gastaba un embed por invocación — un indicador de estado que cuesta dinero termina apagado — y los 9 campos de `StoreStatus` que la UI necesita vivían en tres lugares desconectados.

## Decision

1. **Un FastAPI de SOLO LECTURA que espeja el sobre — cambio de transporte, no capa semántica.** `/query` devuelve **verbatim** el resultado de `server._query` (mismo backend, mismos marcadores, misma regla no-hang §6 que CLI y MCP). Degradado = HTTP 200 (respuesta válida que la UI pinta con su banda); solo `query_unavailable` = 503. `/resolve` (VerifiedRecord completo, bloque 1.4; NOT_FOUND = 200 `resolved:false`) y `/raw` (drill al crudo) idem. Alternativas descartadas (ya razonadas en el handoff): exponer el MCP (riesgo de fiabilidad documentado por ADR-0040) y shell-out al CLI por request (costo de proceso + concurrencia).
2. **`/status` = StoreStatus (9 campos del contrato UI) NO-SPEND por construcción** (receta `liveness.py`): JSON del store (`store_version`, `record_count`, `sha`) + manifest del índice (`index_version`) + Cypher de conteo con timeout acotado (`doc_count`, `entity_count`, `index_state`, `embed_dim`) — **jamás un embed**. Caché TTL (`WITT_STATUS_TTL_SECONDS`, default 60). Neo4j inalcanzable ⇒ `index_state: OFFLINE` + conteos `null` — nunca cifras inventadas. El smoke lo verifica ESTRUCTURALMENTE: monkeypatchea `query`/`query_sparse` con una trampa que revienta si `/status` intenta gastar.
3. **Identidad (decisiones 3/4/9-bis):** 5 cuentas planas (marcelo/natalia/martin = `medico`, emmanuel/sharon = `dev`; el `role` es el `rater_profile`). Passwords con `hashlib.scrypt` (stdlib, n=2¹⁴) + salt por usuario; sesiones = tokens opacos con expiración (`WITT_SESSION_TTL_HOURS`, default 72) de los que la BD guarda **solo el sha256**. **La única asimetría es local**: `seed_users.py` (init/set-password/disable/enable/list) corre en la máquina de Emmanuel — deliberadamente NO existe endpoint HTTP de administración. BD vía SQLAlchemy Core: Postgres en Dokploy (`WITT_BACKEND_DB_URL`, decisión 1) / SQLite local para dev y smokes — un solo code path.
4. **Índice de artefactos históricos (cierra el requisito de ADR-0046):** `/artifacts` lista `reports/*.html` (nombre, `<title>`, mtime, bytes) y `evaluation/runs/**` con `kind: claim_record|aux` (los probes EPS se listan aparte, no se ocultan) e `instrumented: false` donde falta `decision_state` — el corpus histórico se muestra como no-instrumentado, nunca como limpio. `/artifacts/report/{name}` y `/artifacts/run/{set}/{name}` sirven el artefacto; **path-safety por membresía** (el nombre debe existir en el índice; ninguna aritmética de paths sobre input de usuario).
5. **Las cuatro trampas heredadas quedan resueltas en el servicio:** sklearn precargado en el **main thread** en `lifespan` antes de aceptar tráfico (el deadlock de 1800s); `EMBED_MODEL` pineado y `deploy.env` heredados al importar `server`; pool dimensionable (`DI_QUERY_POOL_SIZE`, deploy recomienda 8 para 5 usuarios — el 4 hardcodeado encolaba al quinto). `--workers 1` obligatorio (cachés in-process; la cola de escritura del bloque 5 lo asume).
6. **Alias de la superficie propuesta por la UI** (`/rack/search`, `/rack/resolve`, `/rack/status`) sobre los mismos handlers.

## Consequences

- La webapp tiene su puerta: leer nunca cambia el dato según la puerta (el sobre es idéntico en CLI, MCP y HTTP), y el indicador de estado puede refrescarse para siempre a costo cero.
- Postgres en Dokploy es **aprovisionamiento pendiente de Emmanuel** (crear la app + `WITT_BACKEND_DB_URL` + `seed_users.py init`); el código corre hoy contra SQLite.
- Residuales honestos → bloque 3: `POST /runs` + SSE + modelo de corrida (con el composite-auditor invocable); `/rack/node/{id}` (la operación `browse` sigue sin existir en ninguna puerta); normalización de metadata densa/sparse (§5.9, notada en ADR-0047). Login con tarpit de 0.5s, sin rate-limiting formal (red interna; endurecer si algún día se expone).
- El registro congelado (decisión 2 de ADR-0047: el backend persiste) aterriza sobre esta misma BD en el bloque 3 — `db.py` es su semilla.
